# ADR-0008 叠加规则用策略类加活动配置实现，不引入规则引擎

- 状态：已接受
- 日期：2026-12-04
- 参与：小林（提出）、老陈、营销组

## 背景

算价要支持 7 种券加满减，规则表 6 条（R1～R6），以后每个大促可能加一两种活动。
硬约束：12 天后上线；金额错了要赔，每条规则上线前必须过三方签字的算例；团队没人用过规则引擎。
非目标：这次不让运营自己加新的规则类型，运营只调门槛、力度、预算、时间这些参数。

## 决定

我们把每种优惠写成一个 DiscountRule 实现类，Spring 注入成列表，按规则表 R1 的顺序依次执行；门槛、力度、预算、时间放在数据库的活动配置里，运营可以改。

## 放弃的方案

- 规则引擎（Drools）。输在：12 天里学不会它的调试和上线流程；十几种规则用不上它的冲突检测和决策表。
- 表达式脚本（QLExpress、Aviator 这类），规则存在数据库里。输在：脚本改了不走代码评审和流水线，绕过了“必须过算例”这条硬约束；它换来的“运行时加规则”是非目标。
- 继续写 if/else。输在：420 行已经证明，每加一种都要改同一个方法、重测全部分支。

## 后果

- 好的：加一种优惠是新增一个类；每个类单独测；算例直接当测试。
- 坏的：加新的规则类型仍然要开发、要发布；类会变多。

## 重新看的条件

- 运营要自己加新的规则类型（非目标变成目标）。
- 规则类型超过 30 种，类之间的先后顺序靠代码已经理不清。
