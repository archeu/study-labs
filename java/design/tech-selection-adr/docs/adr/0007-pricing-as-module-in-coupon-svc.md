# ADR-0007 算价放进 coupon-svc 的独立模块，不新建服务

- 状态：已接受
- 日期：2026-12-04
- 参与：小林（提出）、老陈、营销组、订单组

## 背景

运营要在 12.12 上线“满 300 减 40，可和券叠加”。算价现在写在 order-svc 的 OrderService.calcPrice() 里，420 行。
按上下文划分，算价属于营销。营销现有一个服务 coupon-svc（8 台），负责发券、抢券、验券；下单时 order-svc 已经同步调它一次验券。
离上线 12 天。营销是一个小组，4 个人。

## 决定

我们把算价做成 coupon-svc 里和抢券并列的独立模块 pricing，对外只公开 PricingFacade；order-svc 把原来的验券调用换成“算价加锁券”。
模块边界用 Spring Modulith 的 verify() 写成测试，放进流水线。

## 放弃的方案

- 继续写在 order-svc 的 calcPrice() 里。输在：运营每加一种活动都要改订单、发订单；订单是最不该频繁发布的核心链路。
- 新建 pricing-svc。输在：下单要先调券服务锁券、再调算价服务，算价又要回头查券，多出两跳；12 天里还要新建仓库、流水线、数据库和值班表。它买到的独立发布和独立伸缩，现在一个小组用不上。

## 后果

- 好的：下单链路不多一跳；营销加活动不用动订单；以后要拆，搬的是一个接口干净的模块。
- 坏的：算价和抢券在同一个进程里，抢券高峰可能拖慢算价；两者只能一起发布。
- 欠下的：服务名还叫 coupon-svc，名不副实，记入技术债清单。

## 重新看的条件

- 抢券高峰时算价 P99 超过 200 ms，并且把两个模块分组部署以后仍然压不住。
- 营销分成两个小组，每周都有发布互相排队。

出现任何一条，新写一条 ADR 取代本条。
