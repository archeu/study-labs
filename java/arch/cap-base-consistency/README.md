# 3 台 TC 挂了 2 台，下单直接报错：CAP、BASE 与一致性模型

对应页面：[3 台 TC 挂了 2 台，下单直接报错：CAP、BASE 与一致性模型](https://archeu.github.io/study-notes/arch/cap-base-consistency.html)

`CouponQuorum` 是一个模拟，不是真数据库：交易靶场的券状态存在 3 个副本上，1000 张券每张有两单来抢，抢完马上读一次“我锁到了吗”。
网络每 100 个时间片里有一段被分区（随机隔开一台），副本之间异步复制有 1..lag 片的延迟。按 W/R 读写，统计五种组合下的拒绝次数、两单都锁到（要补偿）、读到旧值。
和页面实验台的 JS 是同一套逻辑、同一个随机数（mulberry32），同样的参数输出同样的数字。

## 怎么跑

- IDE：打开仓库的 `java/pom.xml`，运行 `labs.arch.cap_base_consistency.CouponQuorum`，参数 `分区占比 复制延迟 种子`，默认 `0.1 5 42`。
- 命令行：`cd java && mvn -q -pl arch/cap-base-consistency compile exec:java -Dexec.mainClass=labs.arch.cap_base_consistency.CouponQuorum -Dexec.args="0.1 5"`

## 预期输出

JDK 17（`--release 8` 编译）· ARM 2 核 · 种子 42：

```
3 副本 · 1000 张券 · 每张两单来抢 · 分区时间占比 10% · 异步复制延迟 1..5 片 · 种子 42
W R | W+R>N | 抢券被拒(不可用) | 两单都锁到(要补偿) | 刚锁到读成UNUSED | 读被拒 | 恢复后副本不一致
1 1 | 否     |    0 / 2000 |   70 |  538 |    0 | 0
2 1 | 否     |   53 / 2000 |   17 |  284 |    0 | 0
2 2 | 是     |   53 / 2000 |    0 |    0 |   31 | 0
3 1 | 是     |  185 / 2000 |    0 |    0 |    0 | 0
1 3 | 是     |  185 / 2000 |    0 |    0 |  100 | 0
```

再试 `-Dexec.args="0 5"`（不分区，只有复制延迟）：W1R1 仍有 51 张双锁、539 次读旧，这是 PACELC 的 E。

## 练习

先猜结果，再运行。

1. 不用多数派也能读己之写：读请求发给上次写成功的那个协调节点（粘着会话），W1R1 下读成 UNUSED 降到多少？双锁变了吗？
2. N 改成 5，分区时隔开 2 台，比较 W3R3 和 W2R2：哪个出现双锁？哪个拒绝更多？
3. 恢复后按 LWW 定下券的主人，输的那单记一笔补偿；再加一个对账，统计恢复前有多少张券处在不一致状态。
4. 让两单真的并发（两个线程同时“读 R 份、写 W 份”），W2R2 还能保证 0 双锁吗？为什么要一个 leader（Raft）给写排序？
