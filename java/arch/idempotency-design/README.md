# 双击下单只出一张单：幂等设计——唯一键、状态机、去重表

对应页面：[双击下单只出一张单：幂等设计——唯一键、状态机、去重表](https://archeu.github.io/study-notes/arch/idempotency-design.html)

交易靶场 J09 全景“一次下单跨三个库”的第 1、6、8 站。`IdemLab` 连一个 MySQL 8.4，分五段：

- `setup`：建 `orders`、`idem_key`（主键就是幂等键）、`user_coupon`、`stock`、`stock_freeze`（每单一行冻结记录）、`confirm_done`（去重表）
- `entry`：400 个幂等键，每个键来两下，第二下晚到 0..19 ms。先查后插 / 唯一键和订单同一个事务 / 唯一键先单独提交，各出几张单，第二下拿到什么
- `crash`：第一下插完键、还没落单时连接被掐断（`Connection.abort`，模拟 kill -9），同一个键重试
- `state`：券的 Confirm 被 TC 发了 3 次、再来一个迟到的 Cancel；库存两单各冻结 2 件，9527 的 Confirm 发 3 次，“`frozen - 2`”和“冻结记录状态机”两种写法
- `dedup`：300 个分支的 Confirm，1/3 崩在“业务提交”和“记去重表”之间，去重记录单独提交 vs 同一个本地事务；再加 100 组“两个 Confirm 同时到”

## 怎么跑

需要 Docker（会拉 `mysql:8.4`，约 800 MB）。按 JDK 8 写法（`--release 8`）。

```bash
cd java/arch/idempotency-design
./run.sh          # 起容器 → 五段全跑（约 40 秒）
./run.sh again    # 容器留着，只重跑
./run.sh clean    # 删容器（连同数据卷）
```

当前用户不在 docker 组里时：`DOCKER="sudo docker" ./run.sh`。IDE 里运行 `labs.arch.idempotency_design.IdemLab`，参数 `all`（或某一段的名字），先自己起好容器。

## 预期输出

本机 2 核 ARM，JDK 17.0.21，Connector/J 9.7.0，Docker 里 MySQL 8.4.13。跑了两次：写法 1 重复 279～282 个键、写法 3 的 409 有 330～334 次、等待毫秒数会变，其余数字两次一样：

```
[entry] 400 个幂等键，每个键来两下；第二下比第一下晚 0..19 ms（均匀），第一下从判断到落单要 10 ms
  写法 1 先查后插（无唯一约束）：679 张单，279 个键出了两张 | 第二下拿到：{新单=279, 重复，已挡=121}
  写法 2 唯一键，键和订单同一个事务：400 张单，0 个键出了两张 | 第二下拿到：{新单=4, 重放同一单=396}
      其中晚到不足 8 ms 的 156 次，第二下的 INSERT 在唯一键上等第一下提交，平均 13 ms、最多 36 ms，然后才撞上 1062
  写法 3 唯一键，先单独提交键再落单：400 张单，0 个键出了两张 | 第二下拿到：{409 处理中=330, 新单=9, 重放同一单=61}
[crash] 第一下插完幂等键、还没落单时实例被 kill -9（这里用 Connection.abort 掐断连接），用户再点一次，键还是 req-7f3a
  写法 2 键和订单同一个事务：重试拿到「新单」，再试一次「重放同一单」；orders 里 1 行，idem_key 状态 DONE
  写法 3 先单独提交键：重试拿到「409 处理中」，再试一次「409 处理中」；orders 里 0 行，idem_key 状态 PROCESSING
[state] 券 MINUS20（id 7）：Try 锁给 9527，然后 TC 把 Confirm 发了 3 次（第一次的应答丢了）
  Try 9527 改了 1 行；同时另一单 9528 也来锁，改了 0 行
  第 1 次 Confirm：改了 1 行 → 成功
  第 2 次 Confirm：改了 0 行 → 已经是 USED 且属于 9527，当成功返回（幂等）
  第 3 次 Confirm：改了 0 行 → 已经是 USED 且属于 9527，当成功返回（幂等）
  迟到的 Cancel（乱序）：改了 0 行 → 状态已不是 LOCKED，Cancel 不动它（记日志、报警）；券现在 USED / 9527
[state] 库存 sku 88：9527 和 9528 各冻结 2 件，然后 9527 的 Confirm 被发了 3 次
  写法 A `frozen = frozen - 2 WHERE frozen >= 2`：9527 三次 成功 成功 失败 | 9528 的 Confirm 失败（冻结量不够了） | stock 可售 46 冻结 0 已售 4
  写法 B 冻结记录 FROZEN→CONFIRMED，改到 1 行才动 stock：9527 三次 成功 成功 成功 | 9528 的 Confirm 成功 | stock 可售 46 冻结 0 已售 4
[dedup] 300 个分支的 Confirm；每 3 个里有 1 个在“业务改完”和“记去重表”之间崩溃，TC 一直重试到成功
  去重记录单独提交（业务先提交）：TC 调了 400 次，去重表 300 行，已售 800 件（应为 600）→ 多扣 200 件
  去重记录和业务同一个本地事务：TC 调了 400 次，去重表 300 行，已售 600 件（应为 600）→ 多扣 0 件
  两个 Confirm 同时到 × 100 个分支：两次都返回成功的 100 个，已售 200 件（应为 200）
```

怎么读：

- 写法 1 的第二下只要在第一下“查完到插完”这 10 多毫秒里到，就会再出一张单。
- 写法 2 的“新单=4”是第二下反而先拿到了线程，这时是第一下拿到重放；不管谁先，都只有一张单。第二下在唯一键上**等**第一下的事务提交，再撞 1062，所以能直接拿到结果。
- 写法 3 也只有一张单，但第二下多半拿到“409 处理中”；第一下中途死掉时，键永远停在 PROCESSING。
- 写法 A 的总数看起来没错（已售 4），但 9527 的重试吃掉了 9528 的冻结，9528 的 Confirm 反而失败了。

## 练习

先猜结果，再运行。

1. 写法 3 加一个“处理中超过 30 秒就允许接管”：用 `UPDATE idem_key SET created_at=NOW(3) WHERE k=? AND status='PROCESSING' AND created_at < NOW(3) - INTERVAL 30 SECOND` 抢接管权。`crash` 段还卡住吗？第一下其实没死、只是慢了 40 秒时会怎样？
2. 给 `idem_key` 的 `req_hash` 真正存上请求体的哈希，第二下换了数量（2 件改 3 件）用同一个键，返回 422。
3. 把写法 2 的 `WORK_MS` 改成 6000（第一下调外部风控要 6 秒），第二下会怎样？（提示：`innodb_lock_wait_timeout` 在实验里设成了 5 秒）
4. `dedup` 段把“先插去重表、再改库存”换成“先改库存、再插去重表”，两者都在同一个事务里，两个 Confirm 同时到时结果一样吗？锁等在哪一行？
