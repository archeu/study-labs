# 88 号过期那一刻：缓存穿透、击穿、雪崩与大 key、热 key

对应页面：[88 号过期那一刻：缓存穿透、击穿、雪崩与大 key、热 key](https://archeu.github.io/study-notes/redis/cache-five-holes.html)（Java 地图 J07 · 全景“一次商品详情查询”第 4、5、7、1 站）

交易靶场商品服务读详情，带三道防线：第 4 站布隆过滤器挡穿透，第 5 站重建锁挡击穿，第 7 站过期时间加随机数挡雪崩。
为了只看这三道防线，数据库用一个函数代替（每次查 sleep 2 ms，id 1～10000 有货），也没有 Caffeine 本地缓存（见 `java/redis/cache-multilevel`）。

| 类 | 做什么 |
|---|---|
| `ProductCache` | ⑤ 的最小案例：`get(id)` 走 Redis → 布隆 → 抢锁 → 查库 → 回填；每道防线都能单独关掉。另有 `getLogical`：⑥ 里的逻辑过期 |
| `Lab` | 六段实验：`pen` / `hot` / `storm` / `big` / `hotkeys` / `info` |

## 怎么跑

需要 docker（本机不在 docker 组里就用 `DOCKER="sudo docker" ./run.sh`）。代码按 JDK 8 写（Lettuce 6.8.2），布隆过滤器和 `HOTKEYS` 要 Redis 8（8.0 起自带 `BF.*`，8.6 起有 `HOTKEYS`）。

```bash
./run.sh          # 起 Redis 8.10.3 容器（端口 63799），六段全跑
./run.sh hot      # 容器留着，只跑某一段
./run.sh clean    # 删掉容器
JAVA="java -DbigKb=200" ./run.sh big    # 大 key 换成 200 KB
JAVA="java -Draw=true" ./run.sh storm   # 雪崩段再打印每 250 ms 的原始计数
```

| 段 | 做什么 | 对应页面 |
|---|---|---|
| pen | 1 万个随机的、不存在的 id：裸查 / 缓存空值 / 布隆过滤器，各查库几次，Redis 多存了什么 | ②、⑤ |
| hot | 88 号刚过期，4 个实例 × 50 个线程同时查，10 轮：裸查 / 重建锁 / 逻辑过期 | ②、⑤、⑥ 第三圈 |
| storm | 2000 个 key 同一时刻预热、都是 3 秒过期，对比 3 秒 + 0～3 秒随机 | ②、⑤ |
| big | 一条共用连接上，16 个线程读 648 B 的 88 号；旁边有人读 2 MB 的大 key。再 DEL / UNLINK 一个 100 万字段的 Hash | ⑥ 第一圈、第三圈 |
| hotkeys | Redis 8.6 起的 `HOTKEYS START / GET`：按 CPU 时间和网络字节各排前 5 名 | ⑥ 第三圈 |
| info | 几个默认配置：淘汰策略、lazyfree | ⑥ 版本差异 |

- `hot` 的“没过期”是对照：本机只有 2 核，200 个线程一起放出去，光排队就要 19 ms。和它比，重建锁多等了约 30 ms（没抢到的每 10 ms 回头看一次），逻辑过期几乎不多等，代价是大部分请求拿到的是旧值。
- `big` 换成 200 KB（`-DbigKb=200`）时，本机回环上看不出差别：小 GET 的 p50、p99 和没有大 key 时在同一个范围里抖。2 MB 才明显。真实网络上，带宽会比回环先成为瓶颈。

## 练习

先猜结果，再运行。

1. 把重建锁的 `px(3000)` 改成 `px(1)`（比查库的 2 ms 还短），跑 `hot`：每轮查库还是 1 次吗？
2. 把 `bloomInit` 的误判率从 `0.001` 改成 `0.1`，跑 `pen`：布隆过滤器那一行，每轮会漏几次到数据库？再同时打开缓存空值，第 2 轮呢？
3. 把 88 号复制成 8 份：写的时候写 `product:88#0`～`product:88#7`，读的时候随机挑一份，跑 `hotkeys`：`by-cpu-time-us` 的第一名变成谁了？这个办法在 Redis 集群里为什么有用、单节点里为什么没用？
