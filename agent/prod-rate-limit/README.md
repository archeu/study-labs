# 限流和配额：供应商的速率上限、自己的令牌桶

对应页面：[限流和配额：供应商的速率上限、自己的令牌桶](https://study.ainiya.de/agent/prod-rate-limit.html)

全景“大促夜里 1000 个告警同时涌进来”第 ④、⑦ 站。把那一夜按 30 倍速重演 5 遍，比 5 种限流做法。

| 文件 | 做什么 |
|---|---|
| `fake_provider.py` | 假供应商（FastAPI）：`POST /v1/messages` 按 RPM / ITPM / OTPM 三个令牌桶限速（容量 = 10 秒的量），ITPM 只算没命中缓存的输入，带 `cache_control` 的前缀 5 分钟内命中缓存；超了回 429 `rate_limit_error`，带 `retry-after` 和 `retry-after-ms`；`GET /stats` 看计数（按请求头 `x-tenant` 分租户） |
| `bucket.py` | 自己的桶：`TokenBucket`（按 token、可借债放行大请求、预扣后多退少补）、`TenantBuckets`（按权重死分）、`FairBucket`（一个全局桶 + 加权公平排队，P0 先拿，份额是保底不是天花板） |
| `night.py` | 87 个事件按全景节奏到达，16 个 worker，每个调查 6 轮；用官方 `anthropic` SDK（`max_retries=2`）调假供应商 |

没有真模型，也不需要 API key。

## 怎么跑

```bash
cd agent && uv sync
uv run python prod-rate-limit/night.py      # 约 2 分钟（场景时间约 60 分钟）
uv run pytest prod-rate-limit/
```
