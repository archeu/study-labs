# 压测和故障演练

对应页面：[压测和故障演练](https://study.ainiya.de/agent/load-test-drill.html)

全景“大促夜里 1000 个告警同时涌进来”第 ⑥、⑪ 站，站 10 的过关材料：一份压测报告和三份故障演练记录。

| 文件 | 做什么 |
|---|---|
| `harness.py` | 小值班助手：开环按时间表放事件，16 个 worker，主模型 36 万 / 备用 13.5 万 ITPM 的令牌桶，熔断器，每个事件的截止时间，只在网关一层重试，工具层可以注入“工具挂掉”；调用走官方 anthropic SDK |
| `fake_provider.py` | 假供应商（从 `prod-reliability` 拷来），加了 `POST /control`：运行中改卡住比例、529 比例、主模型额度 |
| `breaker.py` | 熔断器和令牌桶（从 `prod-reliability` 拷来） |
| `run.py` | 压测 1×、2×、3× + 演练：模型超时、额度砍半、查日志的工具挂了 |

没有真模型，也不需要 API key。30 倍速：场景 1 分钟 = 墙上 2 秒。

## 怎么跑

```bash
cd agent
uv run python load-test-drill/run.py      # 约 4 分钟
uv run pytest load-test-drill/
```

## 练习

1. `mult` 取 1.5、1.75（到达数要取整），找到积压开始退不下去的那一级。
2. 有 API key 的话，用真供应商跑 20 次同样的调查，按真实的耗时和 token 数改 `GEN_TPS` 和每轮输入，再压一遍 1×。
3. P0 的单次超时改成 20 秒、熔断加“慢调用比例”，再演练 1：转人工的 P0 还剩几个？
4. 起两个 harness 各带 8 个 worker、各一个令牌桶，共用一个假供应商：429 会怎样？
